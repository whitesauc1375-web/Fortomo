# README

## 1. サービス概要

お金のことが不安でも、何から見直せばよいかわからない人が、支出を見直すきっかけをつくるアプリです。
残したい支出と見直せそうな支出を整理し、具体的な手順を確認できます。
将来的には、見直しで生まれたお金をどう使うかまで考えられるようにしたいです。


## 2. 開発のきっかけ

自分自身がお金のことで苦しかったときに、同僚からお金にまつわる制度を教えてもらったことがきっかけです。
そこから少しずつ調べるようになり、お金に対する考え方や行動が変わって、生活も楽になりました。

この経験から、自分も誰かのお金の困りごとに寄り添い、その人が今の生活や将来のために行動するきっかけをつくりたいと思いました。


### 2-1. きっかけとなった体験・感情

お金がなく、一番苦しかった20代後半の頃は、保険もスマホのプランも、内容をよく考えずに契約していました。仕事はしていましたが、お金の使い方を振り返ることはあまりなく、貯金もほとんどできていませんでした。

そんな中で、結婚式への出席が重なったり、不意の出費があったりするたびに、生活が苦しくなっていました。

あるとき、当時の同僚に「ふるさと納税」を教えてもらいました。「こんな制度があるんだ、使わない手はない」と驚き、それをきっかけにYouTubeなどでお金について調べるようになりました。
支出を減らす方法や収入を増やすこと、貯蓄、資産運用など、それまであまり考えていなかったことに関心を持つようになりました。

調べたことを少しずつ行動に移すうちに、生活に余裕ができ、将来のことも以前より考えられるようになりました。この体験が、アプリを作りたいと思ったきっかけです。



### 2-2. お金の不安を減らしたい理由

自分にとって、お金の余裕がないことは、大きなストレスでした。
日々の支払いに追われることや、お金を理由にやりたいことをあきらめることがつらく、気持ちに余裕がなくなることもありました。

子どもの頃、うちは裕福ではなく、外食や旅行に行く機会も多くありませんでした。友達の話を聞いて、うらやましいと感じたこともよくありました。
そうした経験も、お金のことが気になる理由の一つだと思います。

お金があればすべて解決するとは思いませんが、選べることは増えると思っています。自分や家族が大切にしたいことを、お金だけを理由にあきらめなくて済むようにしたいです。



## 3. 解決したい課題　- その体験の中で、最初に感じた「困りごと」

お金に余裕がないことで、「いろいろなことをあきらめなければならない」ということ。


### 3-1. 本当に解決したい課題は何か

「いろいろなことをあきらめなければならない」ことがなぜ困るのか？

お金に余裕がないことで、次のような不安や困りごとがあると考えています。

- 飲み会や同窓会、結婚式などへの参加をためらい、人と会う機会が減ってしまう。
- 急な出費や将来の生活が気になり、落ち着いて毎日を過ごしにくくなる。
- 結婚や子育て、住まいなどについて考えたときに、お金の面で選択肢が限られてしまう。

ただ、こうした不安すべてをアプリで解決するのは難しいと思っています。


本当に解決したいこと：
「お金のことが不安で何かを変えたいけれど、何から始めればよいかわからない」という状態です。

自分の支出を整理し、無理なく見直せるものをすこしづつ選べるようにしたいです。



## 4. 想定ユーザーについて

### 4-1. 想定ユーザーと利用する場面

年齢設定：
  - 年齢：以前の自分に近い、働いて収入はあるものの、あまり貯金ができず、急な出費や将来のお金に不安がある20〜30代の人を中心に考えています。

  - 理由：自分自身が20代後半に、働いていてもあまり貯金ができず、結婚式への出席や急な出費で生活が苦しくなる経験をしたためです。同じような悩みを持つ人が、何に困り、どんなときに使うのかを具体的に考えやすいと思いました。

生活・状況設定：
  - 生活・状況：毎月の支払いはできているものの、あまりお金が残らない人、将来のことに不安がある人、スマホのプランやサブスクなどを契約したまま、あまり見直していない人を想定しています。

  - 理由：自分も以前が同じ状況だったためです。そのため、まずは身近な支出を確認することが、行動のきっかけになると考えています。


環境設定：
  - 環境：お金について気軽に相談できる相手が身近にいない人、または収入や貯金の話を周囲にしづらい環境の人です。

  - 理由：相談のしづらさや情報の多さによって、何から始めればよいかわからず、行動に移せないが多いように思います。なので選択式の質問と収支・資産の入力を通じて、自分のお金の状況と不安を整理できるようにしたいです。
  さらに、支出を見直す具体的な手順や、増えた手残りの使い道を提示し、自分に合う行動を選べる手助けになればと思います。



### 4-2. 自分とユーザーの距離

自分とユーザーとの距離は全くないように思います。

→ なぜなのか？
自分も、お金に不安がありながら、何をすればよいかわからなかった経験があります。そのため、最初の一歩を踏み出しにくい気持ちは、想像しやすいと思っています。



### 4-3. 最初に使ってもらいたい人・需要の確認方法

- まず最初に使ってくれそうな人は誰か？
- その人は、どんな場面でこのアプリを思い出すか？

最初は、妻や友人、RUNTEQの同期に使ってもらいたいと考えています。
毎月あまりお金が残らないと感じたときや、スマホ代やサブスク代が気になったときに、試してもらいたいです。


- 今の生活の中で、代わりに使っているものは何か？
- それを置き換えてまで使う理由はあるか？

家計簿アプリを使っている方は多いと思いますが、家計簿アプリとは用途が別のアプリなので、置き換えての利用は考えにくいです。



### 4-4. 実際に使ってもらって確認したいこと

次のことを確認したいと考えています。

- 質問や金額の入力で、わかりにくいところや面倒に感じるところはないか。
- 残したい支出を無理に減らすような提案になっていないか。
- 提案を読んで、まず何をすればよいかわかるか。
- 実際に見直してみようと思える候補があったか。

行動できなかった場合も、その理由を聞いて、質問や説明の改善に生かしたいです。



### 4-5. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

MVPでは、次の流れを考えています。

1. 毎月の支出が気になったときに、ユーザー登録をせずゲストとして試す。
2. 気になる支出カテゴリーを選択する。
3. 利用状況に関する簡単な質問に答える。
4. 見直し対象がある場合は、サービス名などを入力する。金額の入力は任意とする。
5. 見直し候補と、その選定理由・確認事項・次の行動を確認する。
6. 自分にできそうな行動を選ぶ。合わなければ、今回は見送る。

本リリースでは、ユーザー登録によってデータを引き継ぎ、生活の変化に合わせて見直せるようにしたいです。

毎日使うことよりも、支出が気になったときや、契約内容が変わったときに、また使ってもらえるアプリを目指しています。

## 7. このアプリで実現すること

### MVPで作る機能（まず支出を見直して行動する）

- ゲストユーザー（未ログイン）機能
- 見直したい支出の登録・更新・削除機能
  （カテゴリー・サービス名などを登録し、月額料金の入力は任意とする）
- カテゴリーと質問への回答に応じた見直し候補・確認事項・次の行動の表示機能
- 提案からユーザーが取り組みたい行動を選ぶ、または今回は見送る機能


#### 見直し候補の選び方と表示内容

カテゴリーごとに質問と判定条件をあらかじめ用意して、ユーザーが選択したカテゴリーと回答に応じて、見直し候補を選びます。
候補には、選んだ理由と、見直しを進めるための確認事項・次の行動を表示します。

サービスごとの詳細な解約操作は掲載せず、実際の手続きは契約先の公式ヘルプで確認するよう案内します。

月額料金は、確認のために操作が中断することを避けるため任意とし、後から追加できるようにします。
気になるカテゴリーを選び、質問に回答したうえで、
見直したい対象がある場合に、その支出の情報を入力してもらいます。

支出額の大小だけで不要と判断せず、利用状況への回答をもとに見直しの選択肢を提示します。
実際に取り組むか、今回は見送るかはユーザーが選べるようにします。



#### 例：サブスクの場合

1. 支出入力欄にてユーザーがカテゴリー一覧から「サブスク」を選択する。
2. 「最近1カ月利用していないサービスはありますか？」と質問を表示させる → ある・ない
3. 「ある」と回答した場合は、対象のサービス名を入力してもらう。
   月額料金は任意とし、後から追加・編集できるようにする。
   金額入力がされた場合には、「解約した場合の年間削減額の目安：〇〇円」と表示する。
     （目安は「入力した月額料金 × 12カ月」で計算する。
      今後12カ月分の支払いがなくなる場合の概算であり、
      実際の削減額は契約条件や解約時期によって異なることを併記する）
4. 入力されたサービスを見直し候補として、確認事項・次の行動を表示する。
5. ユーザーが取り組みたい行動を選ぶ、または今回は見送る。

「ない」と回答した場合は、この条件での見直し候補を表示せず、別のカテゴリーへ進めるようにします。



#### 見直し候補に表示する内容の例

対象：ユーザーが入力したサービス名

確認事項：
- 今後、そのサービスを利用する予定があるか。
- 次回更新日はいつか。

次の行動：
- 契約内容が分かる画面やメールで、更新日を確認する。
- 解約を検討する場合は、契約先の公式ヘルプで解約方法や注意事項を確認する。

ユーザーは、表示された行動から取り組みたいものを選ぶか、
「今回は見送る」を選択できます。




### 本リリースで作る機能

- ユーザー登録機能
- ログインログアウト機能
- ゲストデータ引き継ぎ機能:ユーザー登録時、ゲスト時に保存したリストをログインユーザーのデータとして移行する
- パスワード設定機能
- パスワードリセット機能
- 支出入力ページに、各カテゴリーまたは各支出（対象未定）に対して「開発者の考え」を表示する機能を設け、ユーザーが必要に応じてトグルで開閉できるようにする機能
- 貯蓄・金融資産額の登録・更新・削除機能
- 保険などの見直し対象カテゴリーの追加
- 見直しで生まれたお金の使い道を考えるための案内機能
- 支出の見直しで生まれたお金のうち、積立に回す金額を自由に設定し、想定利回りなどの条件に基づいて20年後・30年後の資産額を試算・比較する機能


お金の使い道の案内は、資産運用の経験に合わせて内容を分けたいです。
  - 運用していない人には、急な出費に備えるお金や、近いうちに使う予定のお金を確認したうえで、貯蓄と資産運用の基本を紹介します。
  - すでに運用している人には、現在の運用状況を整理し、積立額や資産配分を見直す際の考え方を紹介します。



### 投資・保険についての注意点

- 投資
本シミュレーションは、ユーザーが設定した積立額・想定利回りなどの条件に基づいて、20年後・30年後の資産額を比較することを目的としており、将来の運用成果や受取額を保証するものではありません。

そのため、入力画面とシミュレート結果画面に
「このシミュレーションは、入力した条件に基づく試算であり、将来の運用成果を保証するものではありません。実際の運用結果は異なる場合があり、元本割れの可能性も伴います。」
と明記する予定です。



- 保険
保険については、平均支払い保険料のデータと、契約内容を確認するための案内を提示します。
ユーザーが自身の状況に照らして、変更を検討するか、現状を維持するかを選べるようにします。

開発者の考えは参考意見として、統計データや一般的な説明と区別し、必要に応じて開閉できる形で掲載します。



具体的に次の流れで考えています。
1. カテゴリーで「保険」を選ぶ
2. 重視したいことを選んでもらう
「毎月の保険料を抑えたい」「今の保険料と世間の平均支払保険料を比較したい」「今は決めない」の選択肢を表示する

「毎月の保険料を抑えたい」「今の保険料と平均保険料を比較したい」のどちらを選んだ場合も、共通の参考画面を表示します。
   1. 平均保険料のデータを表示する
      単身世帯と2人以上世帯の年代別データを表示する。本人に該当する欄を見てもらえば、入力の負担も実装の手間も減らすことができる
   2. 「変更を検討する」「現状を維持する」の選択肢を表示する
  3. 選択に応じた短い案内を表示する
      「変更を検討する」を選択：「まずは保険証券などで保障内容と特約を確認してみましょう」と表示します
      「現状を維持する」を選択：カテゴリー選択に戻ります

「今は決めない」を選んだ場合：カテゴリー選択に戻ります



平均保険料のデータは、出典・調査年度を添えてアプリ内に用意して、更新時に手動で差し替える形にすれば、外部サービスとの連携や複雑な自動判定は必要ありません。（いずれは自動で差し替え更新をしたいですが今はおいておきます）


平均保険料のデータの近くに、次の説明を添えるようにします。
「平均保険料は参考情報です。必要な保障は人によって異なるため、平均より金額が高いというだけで変更を判断する必要はありません」

## 8. このアプリの懸念点とその対策

### 懸念点①

- 何が問題になりそうか：
  質問への回答や金額の入力が負担になり、行動を選ぶところまで到達できない

- なぜそう思うか：
想定ユーザーには、お金の状況を把握できていない人や、調べる時間をなかなか取りづらい人も含まれるため

- そのために考えている対策：
最初の質問と必須入力を絞ることで、金額は概算でも進められるようにする

---


### 懸念点②

- 何が問題になりそうか：
 提案が本人の事情や気持ちに合わず、押しつけに感じられる

- なぜそう思うか：
 選択式の回答だけでは、家族の事情や本人の価値観を把握しきることがむずかしい

- そのために考えている対策：
 残したい支出を確認し、提案には理由と当てはまる条件を添えるようにする
 ユーザーは、出された提案を見送ったり、別の行動を選んだりできるようにする

## 9. 今後の展開・発展の方向性

### 観点

- ユーザーはなぜ使い続ける？
収入や支出、家族構成などが変わったときに、あらためてお金の使い方を見直せるようにしたいです。

- 続けることで何が変わる？
見直せる支出の判断しやすくなり、無理のないお金の使い方が身につきます。見直しで生まれた余裕資金の使い道まで考えることで、将来への見通しが立ち、不安の軽減につながります。

- 他の人と関わる余地はある？
アプリ内での他ユーザーとの交流機能は考えていません。人と比べず、自分のペースで整理できることを大切にしたいです。

---



### 今考えている発展案

- 機能追加の方向性：
 サブスクの更新月や携帯料金の契約更新時期を登録し、見直しのタイミングを知らせる機能を追加する

- UI・体験の改善：
 入力の途中保存に対応することで、ユーザーの負担を減らす。専門用語には説明を一緒に表示するようにし、提案には理由と具体的な手順を示して、「まず何をすればよいか」がわかる画面にする

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- 言語/フレームワーク：ruby 3.3.6 / Ruby on Rails 8.1.4
- DB：PostgreSQL
- デプロイ先：Render, Neon
- 開発環境：Docker(compose.yml)
- 使用予定ライブラリ・関連技術：
    - pg：RailsからPostgreSQLに接続するため
    - bcrypt：パスワードのハッシュ化
    - Turbo・Stimulus：画面の一部更新・運用経験あり/なしで入力欄を変えるなど、必要な画面操作を追加するため
    - Tailwind CSS：画面のデザイン
    - BigDecimal：積立額や利回りを使ったシミュレーション計算のため
    - RSpec：テスト
    - Rubocop：コードの書き方のチェック

---

### 10-2. 技術選定の比較検討

| 用途 | 候補 | 採用状況 | 理由 |
| --- | --- | --- | --- |
| フレームワーク | Ruby on Rails | 採用 | 学習済みの知識を復習しながら、画面表示・データ保存・入力チェックを一つのアプリで実装するため採用
|
| 画面の操作と更新 | Turbo・Stimulus | 採用 | 質問に応じた入力欄の切り替えや結果表示を、Railsの画面構成を生かして実装するため採用
|
| 画面の操作と更新 | React | 今回は不採用 | まだカリキュラムで学習していないため今回は不採用、しかしカリキュラムも並走して進めていくので学習した段階で採用に変更するかもしれない
|
| データベース | PostgreSQL | 採用 | ユーザー・支出・資産などの関連するデータを保存し、開発環境と本番環境で同じDBを使うため採用
|
| データベース | MySQL | 不採用 | デプロイでNeonを利用する本構成では、PostgreSQL一択となるため不採用
|
| 認証 | Rails標準の認証ジェネレーター＋bcrypt | 採用 | 生成されたコードを読み、ログインやパスワード管理の仕組みを理解、パスワードのハッシュ化も実装するため採用
|
| デザイン | Tailwind CSS | 採用 | 余白・文字サイズ・配色などの自由度が高いため、親しみやすいデザインを実装したいと思ったため採用
|
| 少数を含む計算 | BigDecimal | 採用予定 | 想定利回りなどの十進数を扱い、計算の精度や端数処理を管理するため採用
|
| 自動テスト | RSpec | 採用 | 提案の条件分岐・計算結果・ゲストデータ引き継ぎなど、条件ごとの期待する動作をテストとして整理するため採用



- 今回チャレンジしたい点
StimulusやTailwind CSS、BigDecimalなどはカリキュラムで学んでいませんが、実装にあたって必須になるライブラリになるので、しっかりと調べながら実装していきたいです。

- 不安な点
あれもこれもとやりたいことが出てきたので、本リリースまでに時間がかかりそうなことが不安です。
時間をかけすぎるのも良くないのでそこを気を付けつつも、こだわりは捨てずに作っていきたいです。

### 10-3.開発で不安なことと進め方

1. **完成までに時間がかかる可能性がある**
StimulusやTailwind CSSなど、カリキュラムで学んでいない技術の理解と実装に、想定以上の時間がかかる可能性あります。

対応策：まずはMVPに必要な機能に絞り、各技術を小さく試してからアプリに組み込みたいです。


2. **エラーの原因を特定するのが難しい**
使用する言語やライブラリ・フレームワークなどの理解が不十分な場合、どの部分で問題が起きているのか判断できず、修正に時間がかかる可能性が考えられます。

対応策：一度に多くの変更を加えず、機能ごとに動作確認とコミットを行い、問題の範囲を絞れるようにしていきます。


3. **Issueを使った作業の分け方や進捗管理に慣れていない**
Issueを作成して開発を進めた経験がないため、機能をどの程度の大きさに分けるか、どの順番で取り組むか、作業時間をどう見積もるかなどといった進捗に不安があります。

対応策：まずは小さな作業毎にIssueを作り、作業後に見積もりと実際にかかった時間を振り返り、次のIssueの分け方や計画に生かすようにしていきます。
